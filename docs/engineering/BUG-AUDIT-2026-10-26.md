## 一、已修复（7 条）

### BUG-1 [安全 · 中] SSRF 防护漏 IPv4-mapped IPv6 与 0.0.0.0/8
`data/ai/net/GuardedDns.kt`（及 `search/` 的孪生副本 `SearchEgressGuard.kt`）的
`isBlockedTarget()` 只看 `InetAddress` 的标志位与 CGNAT/fc00::/7：
- `::ffff:127.0.0.1` 这类 IPv4-mapped 形式，`Inet6Address` 的
  `isLoopbackAddress/isSiteLocalAddress` 都不命中，但双栈 socket 实际连到 127.0.0.1。
  （`McpUrlGuard` 的注释声称 `getByName` 能识别该形式——这依赖平台字面量解析是否
  返回 `Inet4Address`，不可靠。）
- `0.1.2.3`（0.0.0.0/8）：`isAnyLocalAddress` 只匹配恰好 0.0.0.0，Linux 把整个 /8 路由到本机。

利用面：被提示注入的 agent 被要求 `web_fetch http://[::ffff:127.0.0.1]:8080/...`
（比如打本机 Web 服务或其他本地 HTTP 服务）。
修复：显式拆 mapped/compatible 形式的内嵌 v4 并按同一规则判定；补 `first == 0`；
两份副本同步修改 + 双边测试（映射私网拦截、映射公网放行）。

### BUG-2 [健壮性 · 中] 未知 annotation 类型会炸掉整条流式响应
`ChatCompletionsStreamDecoder.parseAnnotations` 对未知 `type` / 缺失 `type` 直接 `error()`，
且 `element.jsonObject` 硬转。服务商持续新增 annotation 类型
（`file_citation`/`container_file_citation`/`file_path`…），任何一条出现都会中断整个流、
丢掉已生成回答。注释是装饰性元数据，不值得为它牺牲正文。
修复：`mapNotNull` + 跳过未知/畸形项；新增 `ChatCompletionsStreamDecoderTest`。

### BUG-3 [数据丢失 · 中] OAuth 凭证文件非原子覆盖
Codex/Grok/Gemini 三家 `*CredentialStore.write()` 用 `temporary.copyTo(file, overwrite=true)`
直接流式覆盖唯一的加密凭证文件（含已轮换的 refresh token）。进程在拷贝中途死亡 →
文件截断 → `read()` 静默回退到空状态 → 所有已登录账号连同 refresh token 一起丢失，必须重新登录。
修复：同目录原子 `renameTo`（失败时 fallback copyTo）——与仓内 `MissionSnapshotStore` 的既有做法一致。

### BUG-4 [健壮性 · 中] 会话节点 JSON 解码失败让整个会话打不开
`ConversationRepository.loadMessageNodes` 的分页/逐行恢复逻辑只包裹 DAO 调用
（`SQLiteBlobTooBigException`/`IllegalStateException`），而真正的 JSON 解码
（`toMessageNode` 里的 `decodeFromString`、`Uuid.parse`）不在任何保护内：
一行 JSON 损坏（或恢复了向前不兼容的备份）→ 整个会话加载失败，且注释里说的
“为 corrupt blob 准备的逐行恢复”对这种 corrupt blob 永远不会触发。
修复：`toMessageNode` 改为返回可空，解码失败时记录日志并丢弃单个节点（与现有的
“dropping unreadable node”口径一致），两条加载路径都走它。
⚠️ 已知取舍：被丢弃的节点在下次保存时即从库中消失——这与既有 blob-too-big 分支行为一致；
若想改成“保留坏行等待修复”，需要单独设计。

### BUG-5 [DoS · 中低] 备份恢复解压无任何配额（zip 炸弹）
`BackupManager.stageRestore` 用无界 `input.copyTo(output)` 解压到内部存储：
无单条目上限、无总大小上限、无条目数上限。仓内另外两个解压面
（`ArchiveTools` 2GiB/1GiB/10 万条、`SkillZipImporter` 20MiB/200 条）都有配额，唯独这里没有。
来源可为他人分享的备份文件或 WebDAV/S3 上的副本。
修复：流式计数（声明大小可撒谎）+ 上限（200k 条 / 单条 8GiB / 总量 32GiB）+ 一道可用空间闸
（暂存字节不可能合法地超过暂存开始时卷上的可用空间，因为 apply 只是同卷移动）。

### BUG-6 [健壮性 · 低中] Google 模型列表刷新被单个 `!!` 拖垮
`GoogleProvider.listModels` 对每条模型条目的 `supportedGenerationMethods`/`name`/`displayName`
用 `!!`。任何一条缺字段（Vertex 形态的列表、合作伙伴模型、API 演进）都会 NPE，
整个“刷新模型列表”失败。修复：全部改安全调用，畸形条目跳过，`displayName` 缺省回退到模型 id。

### BUG-7 [正确性 · 低] Telegram 分片会切出 n+2 的超长块；小 n 可死循环
`chunkForTelegram`：`lastIndexOf("\n\n", n)` 的起始下标是**包含**式的，
“\n\n”恰好从 index n 开始时，`+2` 后产出 n+2 长度的块——违反“每块 ≤ n”的自身契约
（当前调用方 `MAX_CHARS=3500` < Telegram 上限 4096，所以暂未被拒，但契约是坏的）。
另：`n ≤ 1` 时代理对回退能算出 cut=0 → 余量不缩小 → 无限循环。
修复：段落搜索起点改到 `n-2`、`n` 下限钳到 2、加进度保底；补两条边界测试。

## 二、仅报告（已确证，未在本 PR 动手）

### SEC-1 [安全默认 · 中] Web 服务一开＝局域网无鉴权可驱动 agent
- 默认：`webServerEnabled=false`（需手动开），但开启后 `webServerJwtEnabled=false`、
  `webServerLocalhostOnly=false` 也是默认，且 Ktor CORS 为 `anyHost() + anyMethod()`。
- 影响：同一局域网任何设备——以及用户浏览器里打开的任意网页（CORS 全开、响应可读）——
  都能调 `POST /api/conversations/{id}/messages` 发消息、调 `POST /{id}/tool-approval`
  批准工具执行。`FilesRoutes` 的路径白名单已经修得很到位，但全局无鉴权仍是主洞。
- 建议（需产品拍板）：绑 0.0.0.0 时强制设密码（JWT 默认开），或 `localhostOnly` 改为默认开，
  或首次开启局域网模式时强提示；同时考虑 CORS 收紧到同源。
- 附带：JWT 签名密钥是明文口令本身（HMAC256，无 KDF），token 泄漏可离线爆破口令；
  TTL 30 天且允许 `?access_token=` 查询参数传递（易进日志/历史）。
  `StatusPages` 把任意异常的 `cause.message` 原样返回给 Web 客户端（含内部路径/SQL 信息）。

### CONS-1 [语义分歧 · 低中] 两套定时语义对同一种写法的解释不同
`TriggerSpec.TimeCron` 的注释写着 “same dialect ScheduledJobs accepts”，实际不然：

| 写法 | 定时任务（CronExpressionParser + cron-utils） | 工作流触发器（TimeCronSchedule） |
|---|---|---|
| `@daily` | 每天 **00:00** | 以“布防/上次触发”时刻为相位的每 24h（15:37 建的任务永远 15:37 跑） |
| `@weekly` | 周日 00:00 | 每 7×24h 相位滚动 |
| `@hourly` | 整点 | 每 60min 相位滚动 |
| `@every 90s` | 向下取整成 `*/1 * * * *`（每 60s） | 精确 90s 周期 |
| `@every 90m` / `@every 2d` | **直接拒绝** | 接受（90min / 48h 周期） |

工作流侧的相位锚定是为稳定性/持久化（有测试锁着，是自觉设计），但与定时任务侧同名不同义，
`TimeCronScheduleTest` 里“@daily armed at 00:05 for the next midnight”的措辞与算出的
00:05 本身就互相矛盾。建议：要么统一语义，要么在两处工具描述/UI 文案里把差别写明，
并修正 “same dialect” 注释。

### SEC-4 [安全卫生 · 低] API key 明文进了第二份落盘文件
`ai/util/KeyRoulette.kt` 的 LRU 实现把**原始 API key** 作为 Map 的键持久化到
`cacheDir/lru_key_roulette.json`（明文）。cacheDir 虽不进云备份，
但这是除设置库之外的第二份明文副本，且清设置不清它。建议存 key 的哈希（如 SHA-256 前 16 hex）
作为索引键，功能不变。

### EDGE-1 [健壮性 · 低] TextToolCallParser 跨 chunk 的零宽字符
`normalize()` 按 delta 逐段运行、没有跨段上下文：若上一段以 `<` 结尾、下一段以零宽字符开头
（`<` + U+200B + `tool_call>` 被切成两段流式下发），零宽字符在新段里“前邻居为空、后邻居是 t”，
不会被剥掉，标签识别失败 → 工具调用以原文文本泄漏。概率低、修法略绕（需要把段尾的 `<` 与
段首零宽一起纳入 withheld 尾部），先记档。

### EDGE-2 [计价口径 · 低] 空价格行会压制提供商元数据兜底
`UsagePriceResolver.ratesAt`：用户价格行**存在但四项全空**时，返回空的 UNIFORM 费率
而不是落到提供商的 per-token 元数据兜底；`costMicros` 对空费率返回 null ⇒ 整批调用记为
“未定价”，哪怕元数据里有价。若“用户建了行＝完全接管定价”是有意口径，建议在设置 UI
提示“留空将禁用自动定价”；否则应在行全空时落回兜底。
（附带：`PeakWindow` 跨午夜窗口在 00:00 之后的那一段，按**次日**的星期几判定
`daysOfWeek`；若运营口径是“窗口起始日”，跨夜窗口要把星期几写在次日，容易配错。）

### MINOR 若干
- `WebServerManager.start()` 的 `server != null` 早退在锁外：两个并发 start 分别排队时，
  第二个 `startBody` 会用**它自己那份参数**（端口等）把 state 写成 running，与实际监听不一致。
- `SshTool` 的超时 deadline 用墙钟（`System.currentTimeMillis`），用户改系统时间可提前/拖长超时；
  仓内其他超时多已改用单调钟（`elapsedRealtime`）。
- `TextChunker.ChunkSpec.MIN_CHARS_PER_TOKEN` 命名与算式相反（实际表达的是“每字符最多 2 token”的保守界），
  行为与注释“预算取窗口字符数的一半”一致，仅常量名误导。

## 三、复核过且认为是干净的（避免下次重复劳动）
- Zip Slip：`ArchiveTools`、`SkillZipImporter`、`PendingRestore.resolveInside` 都有 canonical + 分隔符前缀检查。
- 无头审批：`HeadlessToolApprovalPolicy` 的黑名单名均与实际注册工具名对得上；
  `GenerationLoop` 在执行前对每个工具过 `headlessRefusal`，不在仅审批通道里。
- 外部自动化：`ExternalAutomationActivity.verifiedCallerPackage` 正确拒绝了可伪造的 `EXTRA_REFERRER`。
- Telegram bot：严格白名单 fail-closed（空名单丢弃全部）。
- Room 迁移链 v1→v39 完整（AutoMigration + 7 条手写迁移），`ImportedDatabaseReconciler.EXPECTED_VERSION=39` 与 schema 39 一致。
- 向量检索：`VectorMath.cosine/l2Normalize` 对零向量/NaN 均有防线，排序层跳过非有限分数。
- 备份提取规则：`data_extraction_rules.xml`/`backup_rules.xml` 与敏感目录清单对得上（deny-by-default）。
- 凭证加密：OAuth 三家与工作流 SecretStore 均 AES/GCM + AndroidKeyStore（本次问题只在写入原子性，不在加密本身）。
